Core mental model: Microservices are not primarily “small applications.” They are independently owned, deployable business capabilities with explicit boundaries, contracts and operational responsibility.
01

Microservice Fundamentals

Start with the boundary, not the technology.

Problem

One application becomes one change bottleneck

Large codebases accumulate dependencies between teams, releases and business capabilities. A small change can require a large regression cycle.

Solution

Independent business capability

A microservice owns a cohesive capability, its behavior and normally its data. It can be changed and deployed with minimal coordination.

Service boundary

Bounded context + ownership

A good boundary follows business language, data ownership, change patterns and team responsibility—not merely technical layers or database tables.

When not to use

Complexity must earn its keep

For a small team, early product, simple domain or tightly coupled transaction model, a modular monolith can be the better architecture.

02

Service Decomposition & Architecture

The hardest microservices decision is where to draw the lines.

Decomposition

Business capability beats technical layer

“Order service” usually has stronger ownership boundaries than “Controller service” or “Database service.” Decompose around business responsibilities.

DDD

Bounded contexts expose different models

The word “customer” can mean different things in sales, billing and shipping. Each context can own the model that fits its responsibility.

Cohesion

Keep related change together

High cohesion means a service contains behavior that changes for related reasons. Low cohesion produces coordination and deployment noise.

Conway's Law

Architecture follows communication

If teams are split around services, ownership becomes clearer. If every decision requires every team, the architecture tends to become coupled.

Rule: A service should have a reason to exist beyond “we wanted another deployment.” Its boundary should protect business ownership and reduce accidental coordination.
03

Service Communication

Every remote call introduces latency, failure and coupling.

Synchronous

Ask and wait

REST or gRPC is useful when the caller needs an immediate answer. It is easy to reason about but propagates latency and dependency failures.

Asynchronous

Publish work or facts

Messaging decouples timing. The producer can continue while consumers process later, but the system must handle duplicates, ordering and eventual consistency.

API composition

Aggregate at a deliberate boundary

A gateway or BFF can combine service data for clients. Avoid making clients understand internal service topology.

Trade-off

Fewer calls usually means fewer failure edges

Chatty service-to-service calls create latency chains. Prefer cohesive APIs and events where immediate request/response is not required.

GET /orders/42
        |
        +--> Order Service
                 |
                 +--> Payment Service
                 +--> Inventory Service

Risk: latency and failure can propagate across the chain.

API Gateway & Edge Architecture

Hide internal topology and enforce cross-cutting edge policies.

Web / Mobile
→
API Gateway / BFF
→
Order
Catalog
Customer

Gateway

Routes requests, applies edge policies, can terminate authentication and sometimes aggregates responses.

BFF

Tailors an API to a specific client experience. A mobile application may need a different response shape from a web application.

Gateway ≠ Load Balancer

A load balancer distributes traffic. A gateway understands API concerns such as routes, policies, authentication and transformations.

Keep business rules out

Do not turn the gateway into a second business application. Core business decisions belong to the owning service.

05

Service Discovery & Networking

Instances move; clients need a stable way to find them.

Discovery

Service discovery maps a logical service name to currently available instances. DNS, registries and platform-native discovery solve this in different ways.

Client vs server discovery

Client-side discovery chooses an instance directly. Server-side discovery delegates selection to a router or load balancer.

Health-based routing

Traffic should avoid instances that are alive at the process level but unable to serve meaningful requests.

Service mesh

A mesh can move networking concerns such as mTLS, traffic policy and telemetry out of application code, at the cost of platform complexity.

06

Data Ownership & Persistence

Service independence is impossible if everyone owns everyone else's tables.

Order
→
Order DB
│
Payment DB
│
Inventory DB

Database per service

The service owns its schema and persistence decisions. Other services consume contracts or events rather than directly querying its tables.

Shared database problem

A schema change can require multiple teams to coordinate. Direct cross-service SQL creates hidden coupling and weakens deployment independence.

Polyglot persistence

Different capabilities may choose different stores when justified by workload, consistency and operational expertise. Do not introduce technologies merely for novelty.

CQRS & read models

When read needs differ from write ownership, build a read model from owned data/events rather than creating shared-table dependencies.

Distributed Transactions & Consistency

A local transaction boundary stops at the service boundary.

Order Created
    |
    v
Payment ──success──> Inventory
    |                   |
    X failure           X failure
    |                   |
 compensate          compensate / retry

Saga = sequence of local transactions + compensating actions.

Local transaction

A database transaction protects atomic changes inside one transactional resource. It does not make several independent databases one transaction.

Eventual consistency

Different services may temporarily disagree while events propagate. The architecture must define acceptable states and recovery behavior.

Choreography

Services react to events without a central coordinator. It can be elegant for simple flows but becomes difficult to visualize as workflow dependencies grow.

Orchestration

A workflow coordinator explicitly drives steps and compensation. It adds a coordinator but can make complex business processes easier to reason about.

08

Messaging & Event-Driven Architecture

Decouple time and ownership without pretending delivery is magic.

Event vs command

An event describes something that happened: OrderPlaced. A command requests an action: ReserveInventory.

Producer

Publishes a message without needing to know every downstream consumer. This reduces direct temporal coupling.

Consumer groups

Consumers can share work across instances. The exact delivery and ordering semantics depend on the broker and design.

DLQ

A dead-letter destination isolates messages that repeatedly fail processing so they can be inspected or repaired without blocking normal traffic.

Reliability & Resilience

Distributed systems fail partially, slowly and unpredictably.

ControlProblemKey caution
TimeoutDependency never respondsChoose a budget that fits the user/request SLO.
RetryTransient failureRetry only safe/idempotent operations; retries can amplify outages.
Backoff + jitterMany clients retry togetherSpread retries over time.
Circuit breakerRepeated dependency failureFail fast while the dependency is unhealthy.
BulkheadOne dependency consumes all resourcesIsolate pools, queues or concurrency.
Rate limitTraffic overloadProtect capacity and make overload explicit.
Classic failure: A slow downstream service causes request threads to pile up → upstream latency rises → retries increase traffic → the whole system collapses. Resilience controls must be designed together.
10

API Contracts & Versioning

Independent deployment requires compatibility discipline.

Contract

The API contract defines what consumers can rely on: shape, semantics, errors and compatibility expectations.

Schema evolution

Prefer additive changes. Add optional fields before consumers depend on them; avoid removing or changing the meaning of fields abruptly.

Consumer-driven contracts

Consumers express the interactions they depend on. Provider changes can then be checked before deployment.

Versioning

Version only when compatibility cannot be preserved. A version number is not a substitute for a disciplined evolution strategy.

// Safer evolution
{
  "id": "42",
  "status": "PAID",
  "currency": "INR"   // additive field
}

// Risky evolution
"status": "PAID"     // changes meaning or removes old states
11

Security

Every service is a security boundary, not just an internal endpoint.

Authentication

Establish who or what is calling. OAuth2 and token-based resource-server patterns are common at API boundaries.

Authorization

Authentication answers “who?” Authorization answers “what may this identity do?” Keep business authorization close to the business resource.

Service-to-service

Internal traffic still needs identity, authorization and encryption. mTLS can provide workload identity and transport encryption.

Zero trust

Do not assume that network location makes a request trustworthy. Verify identity and policy at meaningful boundaries.

Logs

Explain discrete events. Include structured fields and correlation identifiers rather than relying on free-form text.

Metrics

Reveal aggregate behavior: request rate, error rate, latency, saturation and business signals.

Tracing

Connect spans across service boundaries so engineers can see where latency and failures originate.

Health

Liveness answers whether the process is functioning. Readiness answers whether it should receive traffic.

Testing Strategy

The more distributed the architecture, the more expensive full-system tests become.

TestBest question
UnitDoes this component's logic behave correctly?
ComponentDoes the service behave correctly behind its boundary?
IntegrationDoes it work with real infrastructure such as a database or broker?
ContractCan independently deployed consumers and providers still interact?
E2EDoes the critical business journey work across the deployed system?

Use Testcontainers or equivalent real infrastructure for high-value integration tests. Keep E2E coverage focused on critical journeys rather than using it as the only safety net.

14

Deployment & Release

Deployment independence is one of the major reasons to accept microservice complexity.

Independent deployment

A service should be releasable without coordinating every other service. Stable contracts and backward-compatible data changes make this possible.

Rolling

Gradually replace instances. Simple and resource-efficient, but old and new versions coexist temporarily.

Blue-green

Maintain two environments and shift traffic. Fast rollback is attractive, but capacity cost can be higher.

Canary

Expose a small percentage of traffic to the new version and observe behavior before broader rollout.

Database rule: Use expand → migrate → contract. Deploy schema changes that support both old and new application versions before removing old structures.
15

Containers & Kubernetes

Packaging solves consistency; orchestration solves lifecycle and placement.

Container

Packages the application and its runtime assumptions into a repeatable artifact.

Pod

Kubernetes schedules containers in pods. Applications should be designed to tolerate instance replacement.

Service

Provides a stable networking abstraction over changing pod instances.

Autoscaling

Adjusts capacity according to workload signals. Scaling policy must account for startup time, bottlenecks and downstream capacity.

16

Configuration & Environment Management

Deploy the same artifact; vary environment-specific configuration.

Externalized configuration

Keep deployment configuration outside the application binary. This supports environment-specific behavior without rebuilding the artifact.

Secrets

Credentials and keys require dedicated secret handling, access control, rotation and auditability. They should not live in source code.

Profiles

Profiles can express environment differences, but avoid turning them into a maze of divergent application behavior.

Dynamic configuration

Useful for selected operational policies, but changes need validation, ownership, auditability and safe rollback.

17

Performance & Scalability

Scale the bottleneck, not the diagram.

Horizontal scaling

Add instances when workload can be partitioned. Stateless services are generally easier to scale horizontally.

Caching

Reduce repeated expensive work, but define freshness, invalidation and ownership explicitly.

Async processing

Move non-critical or long-running work off synchronous request paths to protect latency and throughput.

Backpressure

Prevent producers from overwhelming consumers. Queue depth, concurrency and admission control become capacity signals.

Capacity model:
Incoming rate → Queue → Workers → Database

If Database capacity is the bottleneck,
adding more Workers can make the system worse.
18

Distributed Workflow & Business Processes

Long-running workflows need explicit state and recovery.

Workflow orchestration

Coordinates multiple services through explicit steps, timeouts, retries and compensation.

State machines

Make valid business states and transitions explicit. This prevents “hidden workflow state” from being scattered across services.

Idempotency

Repeated delivery should not create repeated business effects. Use stable operation IDs or idempotency keys where appropriate.

Recovery

A workflow is incomplete until failure, restart, timeout and partial-success behavior are defined.

19

Maintainability & Governance

Microservices amplify both good engineering and bad engineering.

Ownership

Every service needs a clear team responsible for code, API, data, reliability and operational health.

Platform capabilities

Centralize boring infrastructure capabilities such as deployment, telemetry, security defaults and service templates without centralizing business ownership.

ADRs

Architecture Decision Records preserve why important boundaries, technologies and trade-offs were chosen.

Prevent distributed monoliths

Watch for synchronized releases, shared databases, chatty calls and shared domain models. These are signs that boundaries are not providing real independence.

Microservices Architecture Patterns

Patterns are tools for recurring problems, not mandatory architecture.

API Gateway / BFF

Centralize edge concerns and tailor client-facing APIs while keeping business ownership in services.

Database per Service

Protect data ownership and independent evolution.

Saga

Coordinate distributed business transactions through local transactions and compensation.

Outbox

Persist business state and an event record atomically, then publish reliably to reduce database/event dual-write problems.

CQRS

Separate write ownership from optimized read models when the domain justifies the added complexity.

Event Sourcing

Store state as a sequence of domain events. Powerful for audit/history-driven domains, but operationally and conceptually heavier.

Circuit Breaker / Bulkhead

Limit the blast radius of dependency failure and resource exhaustion.

Strangler Fig

Incrementally replace or extract capabilities from a legacy system instead of performing a risky big-bang rewrite.

Sidecar / Service Mesh

Move selected cross-cutting networking capabilities out of service code. Useful at scale, but introduces another operational layer.

Decision Matrices

DecisionPrefer A when...Prefer B when...
Monolith vs MicroservicesDomain/team is small, transactions are tightly coupled, speed matters.Independent ownership, scaling and deployment are valuable enough to justify distributed complexity.
REST vs gRPC vs MessagingREST: broad interoperability and resource-oriented APIs.gRPC: efficient internal RPC; Messaging: temporal decoupling and event workflows.
Shared DB vs DB per serviceShared DB: transitional/modular architecture where ownership is intentionally shared.DB per service: strong service ownership and independent evolution.
Choreography vs OrchestrationChoreography: simple event reactions.Orchestration: complex workflows needing explicit state and control.
Rolling vs Blue-Green vs CanaryRolling: normal low-cost rollout.Blue-green: fast switching; Canary: progressive risk exposure.

Common Anti-Patterns

Distributed Monolith

Symptoms: synchronized releases, shared schemas, long call chains. Fix: restore ownership and reduce coupling.

Nano-services

Symptoms: trivial services with more network code than business logic. Fix: merge cohesive capabilities.

Retry Storm

Symptoms: an outage creates more traffic. Fix: bounded retries, backoff, jitter and circuit breaking.

Chatty APIs

Symptoms: one request triggers many sequential calls. Fix: redesign boundaries, aggregation or asynchronous workflows.

No Observability

Symptoms: “works locally” but production incidents have no trace. Fix: logs, metrics, traces and operational SLOs from the beginning.

Microservices Without Automation

Symptoms: manual deployment, configuration and environment setup. Fix: platform engineering and CI/CD.
